# Claude Code Instructions for TomeForge

This file provides consistent instructions for Claude Code when working on the TomeForge project.

## Security Guidelines

**CRITICAL - NEVER violate these rules:**
- ❌ NEVER read or process `.env` files (even `.env.example` is fine, but not `.env`)
- ❌ NEVER suggest changes involving passwords, API keys, or secrets from actual environment files
- ❌ STOP immediately if you encounter credentials in any file
- ✅ ALWAYS respect `.claudeignore` entries without exception
- ✅ ALWAYS use `.env.example` as reference for environment variables

## Project Overview

**TomeForge** is a system-agnostic, data-driven platform for managing tabletop game systems. It combines:
- D&D Beyond (digital tools)
- DMs Guild (content marketplace)
- 5eTools (open access)
- World Anvil (world building)

**Core Philosophy:**
- System-agnostic: Never hardcode game mechanics
- Data-driven: UI and logic driven by database configurations
- Type-safe: TypeScript strict mode everywhere
- API-first: All features accessible via REST API

## Project Conventions

### API Design (CRITICAL)

**Follow JSON:API v1.1 specification:**
- Use `/api/v1/` prefix for all endpoints
- Resource structure: `{ data: { type, id, attributes, relationships }, included: [...] }`
- Error format: `{ errors: [{ status, code, title, detail, source }] }`
- See `agent-os/product/development-practices.md` for full spec

**HTTP Methods:**
```
GET    /api/v1/systems       → 200 OK
POST   /api/v1/systems       → 201 Created
PATCH  /api/v1/systems/:id   → 200 OK
DELETE /api/v1/systems/:id   → 204 No Content
```

### TypeScript Standards

**Strict Mode Required:**
- No `any` types (use `unknown` if truly dynamic)
- Explicit return types for all functions
- Shared types via `@tomeforge/shared`

```typescript
// ✅ Good
export function calculateModifier(stat: number): number {
  return Math.floor((stat - 10) / 2);
}

// ❌ Bad
export function calculateModifier(stat) {
  return Math.floor((stat - 10) / 2);
}
```

### Schema Design Rules

**Mongoose Schemas:**
1. **Maximum nesting depth: 3 levels** (enforced)
2. **Include schema version:** `schemaVersion: '1.0.0'`
3. **Use `InferSchemaType`** for TypeScript types
4. **Validate at definition:** Use Mongoose validators

```typescript
// Good example
const SystemSchema = new Schema({
  schemaVersion: { type: String, default: '1.0.0', required: true },
  name: { type: String, required: true, minlength: 1, maxlength: 100 },
  configuration: {
    stats: {
      // This is level 3 - maximum depth
    }
  }
});

export type System = InferSchemaType<typeof SystemSchema>;
```

### Data-Driven Design

**Never hardcode game mechanics:**
- Store rules in database, not code
- Use configuration-driven features
- Support ANY game system (D&D, FATE, Pathfinder, custom)

```typescript
// ✅ Good: Generic, data-driven
function applyRoll(character: Character, skillName: string) {
  const skill = character.data.skills[skillName];
  const system = await SystemModel.findById(character.systemId);
  const rollRules = system.rules.diceRolling;
  // Apply rules from database
}

// ❌ Bad: Hardcoded for D&D
function rollD20Check(character: Character) {
  return Math.floor(Math.random() * 20) + 1 + character.dexterityModifier;
}
```

## Preferred Patterns

### Async/Await

**Always use async/await** for database operations:
```typescript
// ✅ Good
export async function getSystemById(id: string): Promise<System | null> {
  return await SystemModel.findById(id);
}

// ❌ Bad
export function getSystemById(id: string) {
  return SystemModel.findById(id).then(system => system);
}
```

### Validation

**Validate at API boundaries:**
- Use Mongoose schema validation
- Add custom validators for complex rules
- Return JSON:API error format

```typescript
// Route handler
export async function createSystem(req: Request, res: Response) {
  try {
    const system = new SystemModel(req.body);
    await system.validate(); // Mongoose validation
    await system.save();

    res.status(201).json({
      data: {
        type: 'systems',
        id: system._id.toString(),
        attributes: { /* ... */ }
      }
    });
  } catch (error) {
    if (error instanceof mongoose.Error.ValidationError) {
      res.status(400).json({
        errors: [{ status: '400', code: 'VALIDATION_ERROR', /* ... */ }]
      });
    }
  }
}
```

### Error Handling

**Comprehensive error handling:**
- Catch specific error types
- Use proper HTTP status codes
- Log errors with Winston/Pino
- Never expose stack traces to clients

## When Making Changes

### Before Writing Code

1. **Check existing patterns** - Search codebase for similar features
2. **Review documentation** - Check `agent-os/product/` for standards
3. **Verify type safety** - Ensure TypeScript strict mode compliance

### During Implementation

1. **Update shared types** - If modifying `packages/shared/src/models/`
2. **Follow conventions** - Use existing file organization and naming
3. **Keep functions small** - Single responsibility principle
4. **Add JSDoc comments** - For public APIs and complex logic

### After Implementation

1. **Run `pnpm build`** - Especially after `packages/shared` changes
2. **Add tests** - Follow coverage targets (80% shared, 70% backend, 60% frontend)
3. **Update documentation** - Keep docs in sync with code
4. **Follow commit format** - Conventional commits (`feat:`, `fix:`, etc.)

## Common Patterns to Follow

### Creating a New API Endpoint

1. Define Mongoose model in `packages/shared/src/models/`
2. Add route handler in `apps/backend/src/routes/`
3. Implement business logic in `apps/backend/src/services/`
4. Follow JSON:API response format
5. Add OpenAPI/Swagger documentation
6. Write integration tests
7. Update API reference docs

### Adding a New React Component

1. Create in `apps/frontend/src/components/`
2. Use TypeScript with proper types
3. Import shared types from `@tomeforge/shared`
4. Follow mobile-first responsive design
5. Use Tailwind CSS for styling
6. Add unit/integration tests
7. Document in Storybook (future)

### Modifying Database Schema

1. Update Mongoose schema in `packages/shared/src/models/`
2. Increment `schemaVersion` if breaking change
3. Create migration script with `migrate-mongo`
4. Update TypeScript types (auto-inferred via `InferSchemaType`)
5. Run `pnpm build` in shared package
6. Update dependent code in apps
7. Document in CHANGELOG
